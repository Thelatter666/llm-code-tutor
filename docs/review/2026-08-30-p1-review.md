## 一、阻塞级（合并前必须解决）

### B1 · 重建失败后配置与向量不一致 → 静默返回空结果，且零测试覆盖

**现象推演**（审阅方独立推演，后经代码确认）：

`PUT /admin/model-config/embedding`（`backend/app/routers/admin_model_config.py:33-50`）的执行顺序是：

1. `ModelConfigService.update_embedding()` 把 `embedding_provider` / `embedding_model` 改成新值，`revision += 1`
2. `await session.commit()` —— **配置此时已经落库**
3. `await refresh_embedder_config(session)` —— 运行时换成新模型
4. 逐个 KB 调 `RebuildService.rebuild()`

而 `RebuildService.rebuild()`（`backend/app/services/rebuild_service.py:59-69`）捕获异常后：

```python
except Exception as exc:
    logger.exception("知识库重建失败 kb=%s", kb_id)
    # 失败也要放开：卡在 reindexing 会让检索永久不可用
    await self._set_status(kb_id, KB_READY, on_status)
```

**只把 KB 状态放回 `ready`，不回滚配置。**

**后果链**：配置已指向新模型 → 查询用新模型产生新维度向量 → 按报告 7.2 的分区规则去查
`course_chunks_d{新维度}` → 该集合为空或只有重建中途写进去的残缺向量 → **检索静默返回零命中或残缺命中，没有任何错误码**。

这直接违反 spec §9 的「降级必须可见」原则：此处的降级对**学生端完全不可见**，管理员只能靠主动调用
`GET /admin/model-config/embedding-consistency` 才能发现（而该端点按决策 7「只告警不自动修复」）。

**覆盖情况**（已核实）：`tests/` 中不存在任何针对「重建失败后配置与向量一致性」的断言。
`test_embedding_switch.py` 有 19 处 `rebuild` 字样，但无一条 fail/rebuild 组合用例。即该失败路径**零覆盖**。

**建议修复**（推荐做成可单测的服务方法，而非在路由里补逻辑）：

```python
async def switch_embedding_with_rebuild(self, provider, model, kb_ids, ...) -> dict:
    old = {"provider": cfg.embedding_provider, "model": cfg.embedding_model}
    cfg.embedding_provider, cfg.embedding_model = provider, model
    cfg.revision += 1

    failed: list[str] = []
    for kb_id in kb_ids:
        try:
            await RebuildService(self._session).rebuild(kb_id, ...)
        except Exception:
            failed.append(kb_id)

    if failed:
        # 回滚配置，保证「配置 ↔ 向量维度」始终一致
        cfg.embedding_provider, cfg.embedding_model = old["provider"], old["model"]
        cfg.revision += 1
        raise ApiError(5000, f"以下知识库重建失败，已回滚 embedding 配置：{failed}")

    return {"need_rebuild": True, "knowledge_base_ids": kb_ids}
```

路由改为调用该方法，并在 `finally` 中 `refresh_embedder_config`，保证运行时与库内配置一致。

**必须补的测试**：
1. 重建中途注入异常 → 断言 `ModelConfig` 的 provider/model 已回滚、`revision` 再次自增
2. 同上场景 → 断言后续检索仍能命中（旧维度向量 + 旧配置，自洽）
3. 断言该失败路径会抛出业务错误码而非静默成功

**附注：对「按维度分区集合」的评估（非阻塞）**

审阅方实测发现「删集合后重建」同样能换维度，比分区更简单。但经权衡，**认可报告的选择**：

- 分区方案的决定性优势是**失败安全**：旧维度集合在重建期间原封不动，配合上述回滚即可完全自洽；
- 若改用「删集合重建」，一旦重建失败就会留下「无向量但 KB 标 ready」的状态，检索静默空转 —— 正是 B1 要消除的那类问题。

**但由此产生一条强耦合，必须写进 ADR-0007**：
「按维度分区」与「重建失败→KB 回 ready」（决策 6）是一对，前者是后者成立的前提。
若将来有人改为「删集合重建」，决策 6 会立刻变成缺陷。ADR-0007 当前未记录这层耦合，需补一句。

## 二、高优先级（建议与 B1 同批处理）

### H1 · 重建在 PUT 请求内同步执行，长耗时 + 断连即落入 B1 的不一致态

`admin_model_config.py:46-50` 对每个 KB 顺序调用 `rebuild()`，723 切片约 7.3s/个（报告 5.4）。
KB 数量一多，请求会长时间挂起；客户端中途断开同样会留下 B1 描述的不一致状态。

建议：修复 B1 的回滚后风险已大幅下降；进一步可把重建改走 BackgroundTasks + KB 状态 `reindexing`
（spec §8.7 已规定该状态与 5032 语义），由管理端轮询状态。演示规模下是否值得，可由你权衡。

### H2 · 偏离项未回写 spec，spec 与代码已开始漂移

报告的偏离清单有 9 条，其中 3 条是**结构性**的，必须同步进 spec，否则后续批次照 spec 写代码必然对不上：

| 偏离 | 需回写位置 |
|---|---|
| 7.1 `KnowledgeBase` 增加 `status` 列 | spec §5 数据模型表 |
| 7.3 新增 `PUT /admin/model-config/embedding`、`GET /admin/model-config/embedding-consistency` | spec §6.2 端点清单 |
| 7.4 新增 `DocumentParser` 端口（另：Embedder / VectorStore 两个端口 spec §4.3 亦未列） | spec §4.3 端口清单 |

另 7.5（`ApiError.data`）、7.7（零命中 `degraded=true`）属增量且理由充分，可不改 spec，但在
§9 的降级说明里补一句「零命中亦标记 degraded，与哨兵降级靠 `fallback_reason` 区分」更稳妥。

### H3 · 检索质量结论建立在非代表性语料上，阈值判断不可靠

报告 §4 的语料是 3 个切片，长度 **193 / 131 / 37 字**，而 spec §8.2 的目标切片是 **1200 字符**。
即测试语料比生产切片小 6–10 倍。

这直接影响 8.1 的判断：0.2695 这个分数来自一个 193 字的切片。真实 1200 字切片通常覆盖更多主题，
语义稀释只会**更严重**，不会更轻。因此「0.35 是否偏严」这个问题，在当前语料上得不出可靠结论。

建议：补一组**真实粒度**（约 1200 字）的语料做质量回归，再定默认阈值。

## 五、对你提出的两个决策点的裁定

### 5.1 阈值（报告 8.1）—— 采纳 (c)，但需修正一处论证

**裁定：采纳 (c)** —— 保持 0.35 默认，在管理端开放 `score_threshold` 配置。

**但报告对 (a)「降到 0.25」的评估需要修正**：报告自己的数据其实已经否定了 (a)，只是没点破。
看 §4.1 第三行：

| 查询 | 排序算法 | Python 语法 |
|---|---|---|
| 怎么用 Python 写一个快排？ | 0.2695 | **0.2849** |

**错误切片（Python 语法 0.2849）的分数高于正确切片（排序算法 0.2695）。**
若把阈值降到 0.25，两条都会通过，且**错的排在第一位** —— 这比零命中更糟：
零命中至少会触发「知识库无相关内容」的可见降级，错命中则是把无关内容当成引用来源喂给模型。

所以 (a) 不是「引入更多弱相关噪声」这种程度问题，而是**会反转排序**。建议把这条理由补进报告，
作为 (c) 的支撑 —— 它同时也说明 spec §7.2 步骤 3 的「相对截断兜底」是有价值的（分差 0.0154 < 0.15，
两条都不会被相对截断掉，因此绝对阈值是唯一防线）。

**附加要求**：按 H3，先用真实粒度（约 1200 字）语料复核，再定默认阈值。

### 5.2 前端（报告 8.2）—— 不推迟到 P6，与 P2 合并做

**裁定：不同意推迟到 P6。**

理由：
1. RAG 是本项目三个「增强特性」中的两个（课程知识库增强、知识库检索），是题面的核心卖点。
   推到 P6 意味着直到最后一批才能第一次**看见**它工作，中间 P2–P5 全程无法演示。
2. P2（答疑对话）本来就要做学生端 UI —— SSE 流式、citation 引用展示、`degraded` 提示条。
   若 P1 前端推到 P6，P2 会先搭一套前端骨架，P6 再搭一遍，**两批各搭一次**。

**安排建议**：P2 批次一并补齐 P1 缺失的前端 —— 知识库管理页（含上传与 `chunk_indexed/chunk_total`
进度轮询）、检索演示页、`degraded` 提示条。这样 citation 展示与 SSE UI 只搭一次。
