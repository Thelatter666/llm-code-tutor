# 批次与 Agent 档位分配（P2–P6）

- 日期：2026-08-30
- 背景：有两个可选执行 Agent —— 强但贵、弱但便宜。本文给出每个批次的档位分配与依据。
- 适用范围：P2–P6，以及全项目收尾。

---

## 一、判定原则

按重要性排序，逐批打分后决定档位。

### 1. 失败是否可见（权重最高）

便宜 Agent 的缺陷分两类：

- **响亮型**：测试立刻变红、功能直接报错。审得出来，返工便宜 → 可用便宜档。
- **静默型**：功能看起来正常，实际语义错误。会潜伏到答辩现场才暴露 → **必须用强档**。

静默型典型：防抄袭被绕过（泄露完整答案）、沙箱限制未生效（看起来能跑）、级联删除误删审计、配置改了不生效。

### 2. 是否下游地基

后续批次要长在它上面的，骨架歪则全盘歪。典型：前端骨架、提示词装配器、端口抽象。

### 3. 设计决策密度

spec 已写死、照做即可 → 便宜档。需要临场判断与取舍 → 强档。

---

## 二、逐批判定

| 批次 | 档位 | 失败可见性 | 是否地基 | 决策密度 | 关键理由 |
|---|---|---|---|---|---|
| **P2** 答疑对话 + 防抄袭 + 前端 | **强** | 静默 | **是** | 高 | 见下方详述 |
| **P4** 编辑器 + 受限执行器 | **强** | 静默 | 否 | 高 | 安全边界 + 平台差异 |
| **P3** 代码解析与辅导 **+ 两项并入** | 便宜 | 响亮 | 否 | 低 | 确定性输出，测试好写。另并入两项 P2 遗留，见 §六 |
| **P5** 习题 + 错题本 | 便宜 | 响亮 | 否 | 低 | spec 已写死；含大量内容型工作 |
| **P6** 管理后台收口 | 便宜 | 半静默 | 否 | 低 | 页面量大但每页简单；有 2 个敏感点需重点审 |
| **README + 收尾** | **强** | — | — | 中 | 需全局视角，最后单独做 |

### P2 必须强档的四条理由

1. **首次搭建前端骨架** —— 按 8.2 裁定，P1 遗留的知识库管理页、检索演示页、对话页、degraded 提示条全部并入 P2。P3–P6 的页面都长在这套骨架上（路由守卫、Axios 拦截器、Pinia、design baseline），骨架歪则后续全部返工。
2. **防抄袭失败是静默的** —— ADR-0005 已定「豁免只认显式入口，不做推断」，但实现时仍有大量边界（PromptAssembler 装配、底线判定、intent 传递）。一旦推断错，代价是**直接给出完整答案**，且从外部完全看不出来。
3. **SSE 中断是并发 bug 高发区** —— P0 已为它埋了并发回归用例（两流共享单实例，取消一个不影响另一个）。弱档容易做出实例级 cancel，把守护用例改成通过但语义全错。
4. **跨批次对接** —— 要接 P1 的 `RetrievalService`（七步装配链路），还要把防抄袭度量接到 P6 的统计面板。

### P4 必须强档的三条理由

1. **唯一一批"做错可能伤到机器"的** —— 子进程管理、临时目录清理、资源限制。泄漏的进程、写满的磁盘都是真实损害。
2. **平台差异已实测有坑** —— ADR-0003 记录了 macOS 下 `RLIMIT_AS` / `RLIMIT_DATA` / `RLIMIT_RSS` 全部设不进去，只能用 psutil 采样。弱档极可能照抄 Linux 写法，跑不起来。
3. **失败静默** —— 沙箱没生效时代码照常运行，看起来一切正常，直到有人跑死循环。

### P3 / P5 可放心用便宜档

- P3：Python `ast` + JS 解析都是确定性输出，解析错了测试立刻红。工作量小。
- P5：判题三路与掌握度状态机 spec §5.1、§8.5 已写死（含漏选按错处理、mastered 必须可回滚）。判错分测试立刻抓到。约 40 题种子是纯内容工作，正是便宜档的适用场景。

### P6 用便宜档，但两个敏感点必须重点审

页面量大（用户管理、模型配置、日志、仪表盘、防抄袭统计）但每页都是 CRUD + 表格，适合便宜档。两个半静默点：

1. **硬删除级联 + 审计保留**（spec §8.9）—— 删用户时 `AuditLog` 必须保留，删错就是审计断链，且不报错。
2. **配置热生效**（spec §4.2 硬约束 4）—— 改完立即生效不重启。若实现成改了不生效，页面上完全看不出来。

审阅时这两点要单独看测试。

## 三、执行顺序

```
P2  ──强──▶  P3 ──便宜──┐
                        ├──▶  P5 ──便宜──▶  P6 ──便宜──▶  README+收尾 ──强──
             P4 ──强────┘
```

- **P2 先做**，因为它产出前端骨架与 PromptAssembler，是后续地基。
- **P3 与 P4 可并行**：P3 依赖 P2（复用 PromptAssembler），P4 只依赖 P0，两者互不阻塞，可同时派给两个 Agent。
- **P5 排在 P4 之后**：编程题判题要调 P4 的执行器（spec §11 标注 P5 依赖 P1/P2，但实际还依赖 P4 的 `CodeExecutor`）。
- **P6 最后**：收口所有后台页面。
- **README 单独拿出来最后做**：它是全局文档（一键启动、默认密码警示、安全边界声明、12 个功能点对照），需要全项目完成后的全局视角。由某个批次顺手写必然残缺 —— **强档在全项目完成后统一撰写**。

---

## 四、使用便宜档时的四条控制措施

便宜档的主要风险不是能力不足，而是**偏离既有约定**与**写出无效的测试**。对应控制：

1. **提示词里把约定写死**：分层（routers → services → domain → infrastructure）、领域层禁 IO、`CurrentRidDep`、`UTCDateTime`、`ApiError` 错误码表、TDD 步骤、commit 粒度。不要指望它自己从代码里推断。
2. **指定范本文件**：明确要求「照 `app/services/retrieval_service.py` 与 `app/routers/knowledge.py` 的风格写」。给具体文件比给抽象描述有效得多。
3. **先出计划再审，不要直接动手**：便宜档更容易在方向错误的情况下写完整个批次。
4. **要求给出「变异测试指引」**：即「拆掉某处修复后，哪几条测试会失败」。便宜档最容易写出看起来很全、实际不会失败的测试。P1 这条做得好，审阅方照着拆了两处代码、确认 4 条测试真的会失败 —— 这个做法要固化下来。

---

## 五、一句话底线

预算实在紧张时，最低要求是：**P2 与 P4 必须强档**。其余批次用便宜档 + 上述控制措施，风险可控。

## 六、P2 遗留项的裁定（2026-08-31）

P2 提出 5 项待定，裁定如下。其中两项并入 P3，故 P3 的范围相应扩大。

| # | 事项 | 裁定 | 归属 |
|---|---|---|---|
| 1 | 召回弱点解法（查询改写 + 向量/BM25 的 RRF 混合检索） | **独立成项，但现在不做**。等 P6 完成、用真实教材建库后，实测「窄查询零命中率」再决定 | 暂不排期 |
| 2 | Mock 提供方约 0.1s 生成完毕，浏览器看不到流式输出 | **要做**。并入 P3 | P3 |
| 3 | 前端 Markdown 渲染（AI 回答含代码块） | **要做**。并入 P3 | P3 |
| 4 | spec §8.1「若首轮被丢弃则保留最后一轮」歧义 | **确认 P2 的读法正确**，同时改写 spec 消除歧义 | P3 顺带 |
| 5 | lint 存量 34 处（报告误写为 48） | 单开批次，排在 P6 之后，便宜档 | 新增批次 |

### 第 1 项推迟的理由

它是优化不是功能 —— 12 个功能点已全部覆盖，混合检索不对应任何一项。更关键的是**需要真实语料才能验证收益**：现在做等于在 193 字 / 947 字两组合成语料上盲调。
保留为候选项：若实测零命中率高且时间允许，它是很强的答辩亮点（对应「RAG 知识库检索」增强点）。

### 第 2、3 项并入 P3 的理由

两者都直接影响答辩观感，且都是低风险的局部改动，不需要 P2 的昂贵上下文：
- Mock 无延迟 → 无 Key 演示时 AI 0.1s 答完，看不到流式输出，「AI 编程答疑对话」的演示效果归零。
- 无 Markdown 渲染 → AI 回答里的代码是纯文本，而代码高亮是编程教学场景的核心。
- P3 本身就是代码相关批次，顺带做最自然；且它是便宜档，边际成本低。

## 七、P3 范围（含并入项）

在原「代码解析与辅导」之外，增加：

1. **Mock 提供方流式延迟**（改 P0 的产物代码，需谨慎）
   - `Settings` 增项 `mock_token_delay_ms`，默认约 30ms
   - `MockLLMProvider.stream()` 每个 `TextDelta` 之间 `await asyncio.sleep(delay/1000)`
   - **只影响 Mock 提供方，绝不触碰 OpenAI 兼容链路**
   - 必须有测试：延迟开启时流的总耗时应显著大于 0；且 `complete()` 不受影响

2. **前端 Markdown 渲染**
   - 对话页与检索演示页的 AI 回答需渲染 Markdown，代码块要语法高亮
   - **必须防 XSS**：不得直接 `v-html` 渲染未净化的 HTML
   - 沿用 design baseline（配色 / 间距 / 圆角）

3. **改写 spec §8.1 历史截断那句**（消除歧义）
   原句：「截断后若首轮被丢弃，改为保留最后一轮以保证上下文连贯」
   改为：「若累加后一轮都未纳入（即最近一轮本身已超出预算），则强制纳入最近一轮，保证上下文不断裂」
   —— 语义与已实现行为一致，仅消除歧义
