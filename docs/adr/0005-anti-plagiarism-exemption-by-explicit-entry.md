# 防抄袭豁免只认显式入口，不做语义推断

防抄袭三档仅约束 `seek_answer`（求答案 / 求实现）意图；`review_my_code`（评改学生已写代码）与 `judging`（判分）一律豁免。而**意图不做任何推断** —— 它由前端入口按钮显式传入，聊天入口则一律固定为 `seek_answer`。

起因是推断方案存在致命漏洞：学生问「这道题怎么做」时经常会顺手贴上题目给出的示例代码，若按「消息含代码块即判为评改」推断，就会误判为豁免并直接给出完整答案 —— 防抄袭将在最常用的入口被绕过。推断错误的代价（泄露完整答案）与收益不对称，因此豁免必须是契约而非猜测。

同时，若不豁免「评改已写代码」，`strict` 档会让「代码智能解析与辅导」整个功能点失效：学生问「我这段代码哪里错了」，AI 只能回答「我不能给你改后的代码」。

## Considered Options

- **按消息内容推断意图**：零前端改动。但存在上述误判漏洞，且失败代价不对称。
- **用 LLM 分类意图**：准确率更高。每次请求多一次 LLM 调用（成本与延迟），且在 Mock 模式下分类器本身不可靠。
- **不豁免任何意图**：最保守。代价是 `strict` 档下代码辅导与 AI 判分两个功能点自我阉割。

## Consequences

- `POST /exercises/{id}/hint` 的 `intent` 字段为必填，习题辅导界面必须提供「获取思路」与「批改我的作答」两个独立入口。
- 聊天入口无法豁免，学生若想批改代码须走代码辅导页或编辑器页。
