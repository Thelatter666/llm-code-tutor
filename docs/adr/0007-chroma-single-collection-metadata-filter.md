# Chroma 采用单集合 + 元数据过滤

全系统只用**一个** Chroma 集合（`course_chunks`）存放所有知识库的切片，检索时按
`kb_id` 元数据过滤；不为每个知识库建独立集合。

## Considered Options

- **每知识库一个集合**：过滤条件可以省略，删除知识库时 `delete_collection()` 一行搞定，
  语义上更干净。代价是集合生命周期要跟着知识库的增删走 —— 而知识库由管理员在后台随时
  创建/删除，等于把「集合管理」变成一条需要事务保证的新状态机。一旦中途失败，就会留下
  无法从业务表反查出来的空集合。
- **单集合 + 元数据过滤**：集合只建一次，永不删除；知识库的增删退化为带 `where` 条件的
  行操作，与 SQLite 里的 `kb_id` 外键对齐。代价是**每次检索必须带过滤条件**，漏一次就
  会跨知识库命中。

## 修订：集合按向量维度分区（2026-08-30 实测后追加）

实施 P1 时实测发现：**Chroma 集合在被首次写入后就把维度固定下来了，把集合里的
记录全部删光也不会重置**。于是切换 embedding 模型（1536 / 384 / 256 维）后，
即便按 spec §8.7 做了全量重建，新维度的 `upsert` 仍会被拒：

```
chromadb.errors.InvalidArgumentError:
    Collection expecting embedding with dimension of 384, got 256
```

也就是说，单纯「单集合 + 全量重建」在维度变化这件事上**走不通**。修订为：
集合名带维度后缀 `course_chunks_d{维度}`，同一维度的向量仍共用单个集合。

- 维度作为分区键是**自洽的**：查询向量的维度就是索引时的模型维度，因此「用与索引
  时不同的模型去查」在结构上不可能发生，比靠运行时校验可靠。
- 未重建的知识库其向量仍留在旧维度集合里，`list_ids` / `delete_by_kb` / `delete_ids`
  因此跨分区执行；旧维度的向量在全量重建后成为孤儿，由 `gc-orphan-vectors` 清理。
- 删空后的空集合会被自动清除（至少保留一个），避免维度切换留下无法再用的空壳。

### 与「重建失败 → KB 回 ready」是成对设计

审阅方实测指出：**删除集合后重建同样能重置维度**，比按维度分区更简单（已验证属实）。
分区仍然更优，决定性理由不是简洁性而是**失败安全**：

- 分区方案下，旧维度集合在重建期间**原封不动**。因此重建失败时可以安全地撤销
  配置变更，让「配置 ↔ 向量维度」回到自洽状态（见
  `ModelConfigService.switch_embedding_with_rebuild` 的回滚分支）。
- 若改成「删集合重建」，集合在重建的第一步就被删除了。此时重建失败，就会留下
  「知识库标 ready 但一个向量都没有」的状态 —— 检索静默空转，且**无法撤销**：
  集合已经没了，旧的向量也一起没了。

**因此这两条决策是成对出现的，前者是后者成立的前提**：

| 决策 | 内容 |
|---|---|
| 本 ADR | 集合按维度分区，旧维度集合在重建期间不动 |
| 索引/重建决策 6 | 重建失败时把 KB 状态放回 `ready`，避免卡死 |

**若将来有人把本 ADR 改为「删集合重建」，决策 6 会立刻变成缺陷** —— 状态放回
`ready` 等于对外宣称「可用」，而向量已被删除且不可恢复。届时必须同时把决策 6
改成：重建失败时把 KB 标记为 `failed` 或保持 `reindexing` 并配人工介入入口。

同理，`switch_embedding_with_rebuild` 的回滚分支也是建立在本 ADR 之上的：它假设
「撤销配置变更」足以让检索回到自洽。删集合方案下这个假设不成立，回滚逻辑需要重写。

## Consequences

- 端口 `VectorStore.query()` 把 `kb_ids` 设为**必填**参数，并在实现里对空 `kb_ids`
  直接返回空结果 —— 用签名与短路把这个代价固定下来，而不是靠调用方自觉。
- 删除知识库走 `delete(where={"kb_id": ...})` 而非删集合；失败时按 spec §8.6 继续删 DB
  并落审计告警，残留向量由 `gc-orphan-vectors` 兜底。
- 声明规模下（知识库 < 100、切片 < 数万）单集合的检索性能与多集合无实质差别；若将来
  某个知识库大到需要独立索引，可以按 `kb_id` 灰度拆分，不影响端口。
