# 切片按字符数计量，不用 tokenizer

文档切分按**字符数**计量（默认 1200 字符 / 150 字符重叠），不使用 tokenizer 统计 token。

## Considered Options

- **按 token 计量**（引入 tiktoken 或 sentence-transformers 自带 tokenizer）：与模型的
  上下文窗口口径一致，理论上最精确。但课程知识库以中文教材与讲义为主（spec §3.1 假设 4），
  同一段内容在中文与英文下的 token 密度相差 2–3 倍；同一个 1200 的配置，切英文讲义可能
  得到 400 个 token 的小片，切中文讲义却得到 1200 个 token 的大片 —— **切片粒度不可预测**，
  而这恰恰是检索质量最敏感的参数。此外还要为一个纯离线原型引入 tokenizer 依赖与模型文件。
- **按字符计量**：粒度恒定可预测，零额外依赖。`Chunk.char_count` 直接就是切片长度，
  排障时肉眼可读。代价是「1200」这个数字与模型上下文窗口没有严格对应关系。

## Consequences

- 默认值 1200 / 150 是经验值，写入 `domain/knowledge/chunker.py` 的模块常量，
  不开放后台配置（spec §3.2 权衡 8 只开放了 `top_k`）。
- 声明规模下（单文档 < 10MB、总文档 < 500 份）粒度偏差带来的影响远小于「粒度不可预测」。
- 若将来接入英文为主的语料，应重新评估该阈值，而不是改回 tokenizer —— 折中做法是按
  语种分档给不同的字符数。
